# 执行与安全

## 运行时选择

只依据现有材料起草或审阅时跳过运行时路径。需要云端内容时，先使用本地已安装运行时，按实际操作加载当前技能及参考；同一会话仍适用的读取和检测结果直接复用。Docx 操作不额外预读认证技能或执行认证检查；认证依赖按所调用技能的当前规则处理。

`compatibility.json` 保持 v1：顶层 `required_skills` 和 `required_capabilities` 是完整诊断集合，`profiles` 才是日常操作的最小需求：

| Profile | 所需能力 | 所需技能 |
| --- | --- | --- |
| `draft` | 无，不调用运行时脚本 | 无 |
| `docx_read` | `docs.fetch.v2` | `lark-doc` |
| `docx_create` | `docs.create.v2`、`docs.fetch.v2` | `lark-doc` |
| `docx_update` | `docs.fetch.v2`、`docs.update.v2` | `lark-doc` |
| `wiki_resolve` | `wiki.resolve` | `lark-wiki` 及其认证依赖 |
| `destructive_update` | `docs.fetch.v2`、`docs.update.v2`、`risk.confirmation` | `lark-doc` |

普通追加、插入和追加式更正使用 `docx_update`；只有 Wiki 目标才合并 `wiki_resolve`。实际通过 CLI 读取技能时才额外需要 `skills.read`；已有本地技能时不为此探测。其他动作所需能力按对应技能补充，不能因无关能力缺失而阻塞当前操作。

使用现有 `resolve_runtime` 的 `required_capabilities`／CLI 的 `--required-capability` 传入选中的集合；调用 `probe_runtime` 时只提供这些能力的 `capability_commands`。脚本不自动读取配置，不新增 profile 参数；无 `profiles` 的旧 v1 配置仍兼容，可由调用者显式提供所需能力。

采用能力检测，不以版本号建立永久白名单。版本 1.0.72 是已验证证据和固定回退版本，不是版本上限。不得使用 mutable、latest 或未固定回退。仅在用户已授权下载回退时使用固定 npx 包；没有授权则说明缺失能力并请求该项授权。常规探测只检查版本和所选能力的帮助，不安装、不认证、不访问真实文档。

## 身份与权限

默认使用用户身份，不自动切换机器人。权限不足时说明缺失动作，只请求当前操作所需的最小权限。不得把认证状态、凭据或响应原文写入日志或私有档案。

## 写前解析

创建前检查目标父级中是否已有同名文档。父级 token 与父级 position 互斥，只传一种。Docx 直接核对规范目标；Wiki 目标先解析节点与底层 Docx，再确认写入位置。只有目标唯一且与授权范围一致才写入。

读取完成任务所需的最小范围。只有精确块操作才临时获取块 ID，操作结束后丢弃。写入前记录当前 revision、稳定标题、逻辑锚点、预期相邻内容和正文摘要。

## 并发与幂等

使用当前 revision 做乐观并发控制。revision 冲突后重新读取最小范围，重新定位逻辑锚点并重新生成补丁；不得移除并发修改或用旧块 ID 重试。

创建和追加都不是天然幂等操作。执行前检查同名目标、稳定标题、逻辑锚点和预期正文。超时后重复相同检查，确认未写入后才能重新执行。不得用重复命令赌第一次失败。

## 结果未知

进程超时、响应缺失、warning 非空、`partial_success`、媒体上传状态不明或返回无法解析时，将状态标记为“结果未知”。先读回规范目标并核对位置、锚点和预期内容，不盲目重试，也不把未知报告为失败或成功。

媒体上传不明时同时检查正文引用和媒体可访问状态。读回发现正文已经存在时停止重试；正文部分存在时展示差异并请求用户决定修复方式。

## 授权与普通追加

先判断会话中的任务意图。用户只要求草稿、审阅或规划时禁止云端写入，即使目标有长期信任记录。写入授权可以来自当前消息或同一会话中尚未撤销、仍覆盖当前目标和操作的明确要求，不要求用户每轮重述。

普通追加可依据以下两条路径之一执行，两者都须完成实时目标、隐私、revision、稳定锚点、保护区域与查重检查：

1. **会话内明确授权**：用户已明确指定或确认目标与追加范围，且身份、受众和操作范围未变。直接执行，不要求存在 profile、grant 或解析器的 `may_mutate=true`，也不为获得该值创建档案。
2. **复用长期信任**：用户有明确写入意图，使用私有档案复用此前授权时，实时规范 URL 与目标 token 必须精确匹配；Wiki 还须将实时底层 Docx token 作为 `--backing-document-token` 传入。`private_memory.py resolve` 对本次 `user` 身份、日志类型、受众和 `append`／`block_insert_after` 返回 `may_mutate=true`、`trust_status=trusted` 后直接执行。

向解析器传入最终实际执行的 `--write-operation`：文末追加与锚点后插入不能混用授权结果；操作改变时重新按实际范围核对，不能把 `append` 的受信结果当作 `block_insert_after` 的受信结果。

`may_mutate` 只表达持久信任路径的判定，不代替对会话授权的判断。记录缺失、损坏、过期、撤销或范围不匹配时不能复用该历史授权，也不能应用不匹配的档案；若当前明确授权独立覆盖实时目标，可依第一条路径继续。不得自行修复 grant 或扩大授权。

没有档案不等于目标不明确。仅有别名、多个候选、已授权目标发生漂移或范围改变时，先完成可做的读取和草稿，再澄清缺失或变化部分；不得把用户对旧目标的授权用于新目标。

## 破坏性操作

删除、覆盖、批量重排和历史恢复前，必须展示：

1. 规范目标和精确位置；
2. 受影响标题、块或时间范围；
3. 写前与写后的差异预览；
4. 可恢复方式和不能自动恢复的风险。

先完成上述具体预览，再判断已有授权是否覆盖它。用户已确认同一预览且目标与影响范围未变时直接执行；否则就该预览取得确认，变化时只确认改变部分。事故、审计和决策历史使用追加式更正，不以破坏性操作隐藏旧记录。

## 完整成功判定

只有以下条件全部满足才报告成功：进程退出成功、`ok=true`、业务结果为 `success`、warning 为空、规范目标与位置正确，以及写后读回正文与预期内容等价。

任何一项不满足，都报告已确认的状态、未确认部分和下一项安全核验动作。日志内容仍必须遵守密钥禁入和个人信息最小化规则。
